- MVP scope from the accepted plan: freelancer publishes a service (title, description, price in Pi, delivery time); client browses by category (تصميم، ترجمة، برمجة، مونتاج، كتابة، تسويق); client orders and pays in Pi, funds held by the app first (escrow); freelancer delivers, client approves, app pays the freelancer minus a 10% commission; ratings and reviews after each job. Explicitly out of MVP scope: complex chat and automated dispute resolution.
- `PiGigz - باي جيجز` (user-chosen app name; used as the brand throughout)
- The accepted plan's step 3 states the user registers the app in the Pi Developer Portal and brings the API Key and app wallet themselves, because that step is tied to their own account and KYC. Therefore real Pi SDK payment wiring is NOT possible in this build; the payment flow is built as an explicit Testnet/Sandbox simulation of the Pi payment steps (authenticate → server approve → user sign → server complete), clearly labeled in the UI, with the order/escrow state machine fully real in the database so real SDK wiring later only replaces the payment step.
- `ضيف دخول Pi حقيقي لكل يوزر` (verbatim user request, 2026-11-22 edit): real per-user Pi login. Implemented with the official Pi SDK (https://sdk.minepi.com/pi-sdk.js, loaded in client/index.html): `Pi.init({ version: "2.0", sandbox: true })` (Testnet) and `Pi.authenticate(["username", "payments"], onIncompletePaymentFound)` inside Pi Browser. Each user gets a row in a new `users` table keyed by Pi `uid` with their Pi `username`; gigs/orders/reviews store `seller_pi_uid` / `buyer_pi_uid` so ownership is enforced server-side (only the gig's seller can pause/deliver, only the order's buyer can approve/cancel/review, no self-ordering). The client session (uid, username, accessToken) persists in localStorage and is sent with every mutating action; the server re-verifies the token per call against the Pi Platform API `GET https://api.minepi.com/v2/me` (that endpoint authorizes with the user's own access token, so it does not need the app's Server API Key). If the Pi API is unreachable from the server, the SDK-issued identity is accepted but stored `verified = 0`; a definitive 401/403 or uid/username mismatch is rejected. Outside Pi Browser there is no Pi account, so login cannot complete there — the UI says so and gives the Pi Browser steps; browsing/search stay public. Payments remain the labeled Testnet simulation: server-side payment approve/complete still requires the app's Server API Key from the Developer Portal, which the user has not provided yet. Pre-login gigs/orders have null Pi uids (legacy rows): they stay visible, are badged as pre-login, and any signed-in user may manage them.

- `ضيف الاربعه` (verbatim user request, 2026-11-22 edit): four features added. (1) Per-order chat: `messages` table (order_id, sender Pi uid/name, body); `listMessages`/`sendMessage` verify via the order's buyer/seller Pi uids server-side (`loadOrderParty`), so only the two parties can read or post; pre-login legacy orders stay open to any signed-in user, matching the existing legacy handling. (2) Freelancer profiles: `getFreelancerProfile` by Pi uid aggregates the user's gigs, reviews (including reviews on job-request orders they sold), completed/total order counts and average rating; the verified badge (شارة موثّق) shows after 3+ completed orders (`VERIFIED_BADGE_MIN_COMPLETED`). Bio lives on `users.bio` (`updateProfile`); portfolio gallery is a `portfolio_items` table (title, description, optional external https link, optional category whose existing category illustration is shown) managed by the owner via `addPortfolioItem`/`deletePortfolioItem`. (3) Job requests & offers: `job_requests` (buyer, title, description, category, Pi budget, duration, status open/awarded/cancelled) and `offers` (freelancer, Pi price, delivery days, message, status); `acceptOffer` runs the same labeled Testnet payment simulation and creates a real escrow order with the same 10% commission math, marking the request awarded and other pending offers rejected, atomically via `db.batch`. Orders therefore gained nullable `gig_id` plus `title`, `source` ('gig' | 'job_request') and `job_request_id` columns (migration 0004 rebuilds `orders` and `reviews` to make `gig_id` nullable); gig orders snapshot the gig title into `orders.title` going forward, older rows fall back to the gig lookup. (4) Wallet dashboard: `getWallet` aggregates the signed-in user's own orders only — released net earnings, commission deducted, escrow-pending net/gross and completed/pending counts as a freelancer; completed spend, in-escrow amount and counts as a client; all amounts in Pi, computed server-side from the real orders table.

- Real Pi payments, both directions (user request, 2026-11-22 edit): the official Pi payment flow is implemented end-to-end. Login: `Pi.authenticate` now requests `['username', 'payments', 'wallet_address']`; the stored session key was bumped to `pigigz:pi-session:v2` so every existing user signs in again and grants the new scopes, and the wallet address is stored on `users.wallet_address` (from the SDK result and/or `GET /v2/me`). user_to_app (client pays the app, held in escrow): the server first creates a `payment_intents` row (migration 0006) via `preparePayment` — amount, 10% commission and seller net computed server-side from the gig/offer, never from the client — then the client runs `Pi.createPayment` (SDK already loaded from https://sdk.minepi.com/pi-sdk.js) whose `onReadyForServerApproval` calls `approvePayment` (server re-fetches the payment from `https://api.minepi.com/v2/payments/{id}`, verifies direction user_to_app, payer uid, exact amount and the intent id in the payment metadata, then POSTs `/approve`) and whose `onReadyForServerCompletion` calls `completePayment` (verifies approval + txid, POSTs `/complete`, then creates the escrow order exactly once via the intent). `onCancel`/`onError` call `failPayment`. Incomplete payments reported by `onIncompletePaymentFound` are resolved by `resolveIncompletePayment` right after login: completed on the Platform (and their escrow order created) when approved with a transaction, otherwise cancelled server-side. app_to_user (app pays the freelancer after client approval): `approveOrder` completes the order then runs the server-only payout — POST `/v2/payments` to create the A2U payment, sign & submit the blockchain transaction from the app wallet with `@stellar/stellar-sdk` against the Pi Testnet horizon (https://api.testnet.minepi.com, passphrase "Pi Testnet", payment identifier as memo, destination = freelancer's stored wallet address), then POST `/complete`. Orders store `pi_payment_id`, `pi_txid`, `payment_status` (pending/approved/completed/failed/cancelled/simulated), `payout_id`, `payout_txid`, `payout_status` (pending/submitted/completed/failed/simulated), a deterministic `payout_idempotency_key` (`pigigz-payout-order-<id>`, unique-indexed) plus the stored payout id, so retries (`retryPayout`, either order party) resume instead of ever paying twice; failures are recorded as sanitized `payout_error` text on the order and shown in the UI with a retry button, and the wallet dashboard gained a "payouts still on their way" total. Secrets: the server reads ONLY the environment variable names `PI_NETWORK_API_KEY` and `PI_WALLET_SEED`, inside the host-only privileged handlers in `server/src/privileged.ts` (the action sandbox forbids env access, so actions receive only booleans, parsed Pi API responses and txids back through `ctx.executePrivileged`); no key or seed value is requested, printed, stored, or present in code/chat — the developer enters them in the server secret manager. `getPaymentConfig` exposes only booleans (realPayments / realPayouts). While `PI_NETWORK_API_KEY` is unset the app keeps the previous clearly labeled Testnet simulation for ordering (createOrder/acceptOffer) and instant simulated release, so nothing breaks; real payments and payouts switch on automatically once the developer sets the variables. Cancel-order refunds of already-completed real payments are not automated (Pi has no refund endpoint; they would be a manual A2U payment) — cancellation still only happens pre-delivery and just marks the order, as before.

## Long-term data behavior
- **Refresh policy**: none; no external data and no scheduled refresh. Data changes only through user actions in the UI.
- **Growth**: gigs, orders, and reviews accumulate as the user creates them; lists are paginated by simple newest-first loading (no cap needed at MVP scale).
- **Ordering**: gigs newest-first by default with category filter and text search; orders newest-first; reviews newest-first per gig.
- **Time semantics**: created/delivered timestamps are creation instants stored server-side and rendered viewer-local; delivery time on a gig is a plain day count entered by the seller, not a computed date.

## Rejected approaches
- **Tried**: wiring the real Pi SDK (Pi.authenticate / Pi.createPayment) end-to-end.
  **Why rejected**: the accepted plan assigns Developer Portal registration, API Key, and app wallet to the user (tied to their account/KYC) and that step has not happened; shipping a fake 'connected' state would be dishonest. The UI instead runs a clearly labeled Testnet sandbox simulation over the real escrow state machine.
- **Tried**: seeding the marketplace with invented freelancer gigs so the browse page looks full.
  **Why rejected**: those would be fabricated records presented as real sellers. The marketplace starts empty with a designed empty state and a prominent 'publish your first gig' path; category artwork keeps the browse page visual without fake data.
- **Tried**: live Pi/USD price ticker.
  **Why rejected**: no tested live source in this build and prices are denominated in Pi natively; a stale or invented rate would mislead.
